Технические требования 
Рекомендуется разрабатывать программное обеспечение на платформе Java SE 17 
https://adoptium.net/ и Spring 4. Spring рекомендуется использовать в варианте spring-boot. 
В качестве базы данных рекомендуется использовать СУБД, не требующее установки, как 
например Derby или H2.  
В качестве билд-системы рекомендуется использовать Maven 2 https://maven.apache.org/ 
В качестве сервера приложений рекомендуется использовать встроенный в приложение 
tomcat (автоматически загружается и развертывается maven/spring-boot). 
Выполнение вышеуказанных рекомендаций позволит сократить набор инсталлируемых 
приложений до только платформы Java SE, а набор загружаемых библиотек только до Maven 
2. Все остальные библиотеки и ресурсы Maven загрузит и установит самостоятельно. 
В качестве IDE рекомендуется использовать IntelliJ Idea, Eclipse или Netbeans

Цель compile – компиляция проекта 
Цель package - компиляция проекта и сборка дистрибутива

Протокол http. 
Для понимания того, как устроено веб -приложение, необходимо прежде всего понять, как 
устроен протокол http. Http (hypertext transfer protocol) является текстовым протоколом  
прикладного уровня, выполненным на основе транспортного протокола tcp. Типовое общение 
между клиентом и сервером состоит из выполнения запроса ( Request) и получения ответа 
(Response). 
Запрос состоит из нескольких частей: 
• Метода запроса 
• URI – идентификатора запрашиваемого ресурса 
• Версии протокола  
• Заголовков запроса 
• Тела запроса 
Ответ состоит из 
• Кода ответа 
• Тела ответа 
• Заголовков ответа 
Рассмотрим составляющие протокола подробнее. URI представляет собой адрес ресурса, 
которому отправляется запрос. Он формируется из протокола, имени сервера, номера порта 
и собственно пути, например, http://localhost:8080/mypp/myresource представляет собой 
получение ресурса /myapp/myresource с сервера localhost через порт 8080 по протоколу http. 
Данный путь является абстракцией и может обрабатываться веб -сервером по своему 
усмотрению, т.е. сервер решает, какой именно код обработает запрос по данному пути, на 
основании своей конфигурации, описывающей правила такого сопоставления . Кроме того,

соответствие некоторому идентификатору, который передается на клиент через Cookie. В 
дальнейшем клиент, чтобы обратиться к этой сессии, посылает идентификатор сессии 
обратно.  Однако если клиентская система не разрешает Cookie, то используется URL Rewriting, 
то есть идентификатор сессии автоматически добавляется к каждому URL. Специальный 
механизм – HttpSession API – реализует эти сценарии автоматически и не требует от  
пользователя каких-либо специальных действий.

Предпосылки появления Web API  
При разработке приложений крайне неудобно возвращать всегда непосредственно HTML 
страницы. Это связано с тем, что таким образом мы объединяем логику доступа к данным и 
логику представлений в одном месте. Недостатком такого объединения может быть, 
например, то, что при появлении нового клиента доступ к данным необходимо реализовывать 
и в нем. Эта проблема может быть решена путем вынесения логики доступа в отдельную 
библиотеку, однако возникающие сложности по управлению конфигурациями всех 
программных продукт ов являются причиной появления систем, в которых возможно 
разделение кода на отдельные компоненты, исполняемые на различных машинах, и обмен 
данными по четко специфицированным протоколам. Первоначальное развитие получили 
технологии, основанные на бинарных протоколах, такие как CORBA/IIOP и DCOM/ORPC, через 
которые мультимашинные приложения могли обмениваться информацией.  В частности, 
технология CORBA в своей основе содержит ORB (Object Request Broker) – унифицированную 
шину данных, к которой можно подключи ться и через которую передаются и получаются 
данные. Компонент, желающий выполнять передачу по шине, должен знать контекст адресата 
своего сообщения и выполнять конвертацию вызовов и данных в бинарный формат (процесс 
называется маршаллингом) и из бинарного  формата (демаршаллинг) в соответствии с 
правилами, определенными для языка, на котором этот компонент написан. В результате с 
помощью технологии CORBA можно интегрировать коды на десятках различных языков. 
Тем не менее такие подходы оказались неудобными (прежде всего из-за высокой сложности)

является опциональным.

Развитие REST – Query Data API 
Существуют подходы, основанные REST, и предназначенные для получения данных от сервера 
по определенным запросам, сформулированным клиентом . Прежде всего, это GraphQL 
https://graphql.org/learn/ . В технологии GraphQL на сервер посылается JSON с запросом в 
определенном формате, а назад приходит ответ, опять таки, в определенном формате. Этот 
подход, с одной стороны, гибче REST и позволяет экономить на передаче информации, 
которая не требуюется клиенту, с другой стороны, перекладывает часть логики приложения 
на клиент, что является определенным недостатком. 
Другим развивающимся подходом является OData https://www.odata.org/ . Подход 
представляет собой формальный язык запросов к сервису, выполненный в стандарте REST и 
обладающий высокой гибкостью. 
ORDS (Oracle Rest Data Service) https://www.oracle.com/database/technologies/appdev/rest.html  
является инструментом, автоматически отображающим определенным образом 
сформированные http –запросы на базы данных. 
Сравнительный анализ этих технологий можно прочитать по ссылке 
https://www.progress.com/blogs/rest-api-industry-debate-odata-vs-graphql-vs-ords (англ.).

При программировании для сети Интернет  приложение приобретает другую структуру, 
нежели при программировании для десктопов. Само приложение состоит из двух частей – 
серверной части, или бэкенда (backend), исполняемого где-то в интернете и клиентской части 
или фронтенда  (frontend), исполняемого на клиентской машине в браузере. При этом

детали, связанные с доступом к серверной части, а также следит за безопасностью.

JavaScript. Первые приложения таких типов имели статические клиентские страницы – при 
работе с ними было необходимо отправить на сервер запрос и получить в качестве ответа 
новую страницу. Такой подход иногда используется и сегодня (обычно для простых

Снифферы и атаки “Man-in-the-middle”.  
Сниффер (анализатор траффика) – это программа, которая переводит сетевую карту в режим, 
в котором она анализирует все пакеты в своем сегменте сети, вне зависимости от их адресата. 
Такое программное обеспечение может применяться администраторами сетей для 
обнаружения неправильной маршрутизации трафика; к сожалению, оно же может 
применяться злоумышленниками для перехвата трафика пользователя. Существуют 
инструменты обнар ужения снифферов, но в тот момент, когда системный администратор 
обнаружит вредоносное ПО , захват чужих данных уже произойд ет. Поэтому критически 
важно, чтобы весь трафик, содержащий логины и пароли, был зашифрован (а также грамотно 
настроена маршрутизация трафика, максимально исключая его отправку в сегменты сети, 
которым он не предназначается). 
Другой важной проблемой является злонамеренная конфигурация прокси сервера. В случае,  
если доступ к нему получил злоумышленник, то весь трафик пользователя автоматически 
становится ему доступен. Такая атака называется “человек посередине” или man-in-the-
middle. К счастью, современные алгоритмы шифрования устойчивы к таким атакам, что не в 
последнюю очередь достигается тем, что трафик подписывается цифровой подписью, 
удостоверенной сертификатом, заверенным сертифицированным удостоверяющим центром.

Защита от атак XSS и CSRF.  
XSS – Cross-Site Scripting, специальный вид атаки, при котором вредоносный код пытается 
загрузить в себя часть доверенного сайта и выполнить в нем действия от имени пользователя. 
Существует много различных вариантов этой атаки, начиная с загрузки доверенного сайта во 
фреймы и заканчивая попытками инъекции сценариев в поля ввода доверенного сайта, в 
надежде что эти сценарии будут выполнены и сумеют получить доверенный доступ к 
сценариям самого доверенного сайта.  
Загрузка доверенного сайта полностью или частями во вредоносный сайт в основном 
блокируется современными браузерами на основании политики same-of-origin (единого 
происхождения), то есть требования, чтобы все ресурсы сайта приходили с одного доменного 
имени, протокола и порта. Иногда доверенный сайт использует технологию CORS (Cross-Origin 
Resource Sharing) позволяющую информировать браузер об исключениях в правиле same-of-
origin. Использование этой технологии не рекомендуется с точки зрения безопасности; 
неправильное же ее употребление может привести к уязвимости сайта.

Аутентификация через директории пользователей (Kerberos, LDAP).  
В сложных корпоративных системах зачастую возникает проблема , связанная с тем, что 
одному и тому же пользователю надо назначать права во многих приложениях 
одновременно. В такой ситуации бывает полезно вынести центр аутентификации из 
приложения в стороннюю систему. Примерами таких решений могут быть Kerberos и LDAP (а 
также многие другие). 
Kerberos является протоколом шифрования, при котором аутентификация возможна даже 
если между приложением и центром аутентификации лежит незащищенный канал. Такой 
протокол шифрования, например, используется службой Active Directory. Приложение и центр 
авторизации обмениваются данными о пользователе по специальному протоколу , используя 
симметричное шифрование Нидхема-Шредера.  
LDAP (Light-Weight Directory Access Protocol, легковесный протокол каталога пользователей) 
является протоколом , часто используемым для централизованного хранения имен 
пользователей и паролей. Этот протокол не просто разрешает аутентифицировать 
пользователей, но еще и управлять ими, то есть добавлять, удалять и модифицировать записи. 
Использование аутентификации через директории пользователей удобно в крупных 
компаниях, в которых необходимо иметь единое место ведения информации о 
пользователях. Кроме того, эта модель аутентификации значительно безопаснее, чем Basic и 
Digest, по многим причинам: сервер является внешним для приложения и может быть закрыт 
файрволлом, его безопасность подтверждена аналитиками, правила его безопасного 
использования четко определены и т.п.

SSO аутентификация.  
С развитием облачных технологий, особенно SaaS, возникла новая проблема – организации 
может быть необходимо иметь единый список пользователей, которым могут назначаться 
права в сторонних приложениях. Например, пользователь может работать с системами 
документооборота, управления предприятием и другими,  предоставляемыми в рамках SaaS, 
однако было бы крайне неудобно управлять полномочиями в каждом приложении отдельно. 
Эта задача решается с помощью аутентификации SSO – Single Sign On. В этой модели 
аутентификации существует некоторый провайдер, удостоверяю щий личность и полномочия 
пользователей, интегрированный с используемыми приложениями таким образом, что , 
удостоверив в нем свои полномочия , пользователь получает доступ ко всем приложениям 
сразу. Подобные системы ( Identity Management as a Service) поставляют многие компании  - 
интеграторы.  
SSO аутентификация решает сразу большое количество проблем, такие как необходимость для 
пользователя помнить много разных паролей, создание сертифицированной системы 
безопасности (так как SSO позволяет закрыть сервера файрволлом, пропускающим только 
аутентифицированные запросы), упрощает поддержку и обслуживание систем авторизации и 
аутентификации.

Как мы уже выяснили в первой лабораторной работе, сервлеты могут генерировать HTML код

первых, необходимо контролировать корректность html документа, построенного путем

наоборот – невозможно легко передать результат работы дизайнеров программистам. Также

использование сервлета для прямой генерации HTML документов  является неудобным и ему 
на смену пришли генерации страниц на основе шаблонов, заполняемых данными с сервера .

Основные понятия JDBC. Соединение с СУБД. 
JDBC является технологией, лежащей в основе более высокоуровневых средств доступа к 
базам данных, таких как ORM. Основная идея JDBC состоит в том, что все конкретные детали 
работы с базой данных абстрагирует предоставляемый ее производителем драйвер, а 
программист работает через набор стандартных классов, образующих обертку вокруг него. За 
счет этого обеспечивается некоторая унификация доступа к БД, хотя и в меньшей степени, 
нежели для ORM (например, все равно надо иметь в виду особенности версии SQL). 
В основе работы c JDBC лежит класс DriverManager. Этот класс абстрагирует всю работу с 
драйверами баз данных и позволяет создавать соединения с СУБД, используя перечни свойств 
или URL баз данных.  Такое соединение представлено классом java.jdbc.Connection. Для 
инициализации этого класса требуется информация, специфичная для производ ителя БД. 
Обычно при работе из среды аппсервера созданием экземпляров этого класса управляет 
именно контейнер, а не пользовательский код, соответственно, приложение тем или иным 
образом его от контейнера получает.  Это связано с тем, что получение соединения с СУБД 
является тяжелой операцией, а сами соединения требуют ресурсов, поэтому необходимо ими 
эффективно управлять и переиспользовать. Эту задачу решают пулы соединений.  Одним из 
наиболее популярных решений для переиспользования соединений с БД является Hikari pool.

ORM. Виды ORM.  Стандарт JPA. 
 
Глядя на вышеприведенный код маппера, можно легко прийти к выводу, что он очень 
многословен и неудобен. Было бы гораздо удобнее писать код, если бы существовала 
возможность автоматического преобразования полей базы данных в атрибуты класса. Эту 
идею взяли на вооружение разработчики другой технологии – ORM или Object Relation 
Mapping, в которой весь обмен с базой данных идет через объекты. Для языка Java определен 
стандарт такого взаимодействия, который называется JPA (Java Persistence API). 
Существуют десятки библиотек ORM для Java. Наиболее известной и популярной ORM 
является Hibernate, поддерживающая стандарт JPA. Достаточно часто встречаются  MyBatis и 
EclipseLink, последняя считается эталонной реализацией JPA. 
Рассмотрим архитектуру доступа к данным JPA. В основе доступа к данным находится класс, 
который называется Persistence, который содержит в себе информацию о конфигурации 
соединения с базой данных. Этот класс нужен для конструирования экземпляра класса 
EntityManagerFactory, в свою очередь, являющегося фабрикой экземпляров классов 
EntityManager. Этот последний класс является фасадом устойчивого контекста ( persistent 
context) базы данных, то есть именно через него и осуществляется все взаимодействие 
приложения с базой.  В частности, именно он реализует четыре основных операции с базой 
данных, получившие аббревиатуру CRUD (Create, Read, Update, Delete) с помощью методов 
persist (создать или обновить), remove (удалить) и find (найти).

специальных аннотаций, указывающих на правила связывания их с полями базы данных.

попытке трансформации в JSON будут прочитаны все внешние ключи и потенциально 
возвращенная информация будет гораздо больше по объему, чем необходимо, либо вообще 
процесс зациклится, если в базе есть циклические зависимости. Для решения этой проблемы 
используется большое количества разнообразных техник – отключение записи от базы перед 
трансформацией, специальные аннотации, информирующие JSON трансформер о том, что не 
нужно идти по внешним ключам, но наиболее универсальным является DTO, то есть 
преобразование объекта в другой объект  (который и называется DTO), содержащий только 
нужную информацию и не имеющий связи с базой данных. Это преобразование обычно 
осуществляется специальным маппером, инкапсулирующим бизнес -логику того, что именно 
нужно возвратить клиенту.

Паттерн DTO. 
Начинающий программист испытывает соблазн использовать в API своего сервиса те же самые 
классы, что и для доступа к базе данных. В общем случае это очень плохое решение, так как 
внешние ключи сущностей могут так же быть возвращены на клиент, а это значит, что вместо 
объекта вернется дерево. Более того, если между су щностями имеются циклические 
зависимости по ключам, то это может привести к попытке вернуть результат бесконечного 
размера и последующим падением с исчерпанием памяти. 
Для решения указанной проблемы используется шаблон Data Transfer Object или просто DTO. 
Шаблон состоит в том, что для API используется специализированный класс, который не 
связан с базой данных и не решает больше никаких задач.  Необходимые значения при 
необходимости копируются между объектами этого класса и объектами -сущностями. Более 
того, если имена полей в этом классе имеют те же имена, что и в сущности, то можно 
использовать специальный сервисный класс ObjectMapper, который скопирует поля с 
одинаковыми именами, например, так: 
ObjectMapper objectMapper = new ObjectMapper(); 
ObjectA objA = objectMapper.convertValue(objB, ObjectB.class); 
В этом примере все одинаковые поля из объекта objB класса ObjectB будут скопированы в 
объект objA класса ObjectA. При этом ObjectB должен иметь на них геттеры, а ObjectA – 
сеттеры.

При взаимодействии через REST достаточно серьезной проблемой является синхронность 
взаимодействия, вызывающая пропорциональный рост нагрузки на сервер с увеличением 
числа запросов. Если клиентская система начинает генерировать нагрузку, которую 
нижележащий сервер не в состоянии обработать, такая нагрузка может снижаться средствами 
ограничения трафика. Однако есть и неустранимые проблемы, например, если в рамках 
обработки какого -либо запроса должны быть задействованы несколько систем, то при 
синхронном взаимодействии время обработки одного запроса будет складываться из времен 
обработки всех запросов, участвующих во взаимодействии.  
Решением проблемы может является перевод части действий, не формирующих 
непосредственный ответ API, в асинхронный режим. Типовыми случаями являются задачи 
нотификации таких частей системы, как журналирование, биллинг, BI о произошедших при 
обработке существенных изменениях, которые могут осуществляться путем посылки 
сообщения, которое обрабатывается асинхронно вне контекста запроса.  
В ряде случаев, для систем, которым требуется особенная устойчивость к нагрузкам, 
синхронное взаимодействие может полностью меняться на асинхронное (и, соответственно, 
взаимодействие с ними клиентов будет осуществляться не по протоколу http , а через 
вебсокеты). В этом случае клиент имеет некоторую модель состояния сервера, а сервер его

отправить. Клиент отправляет событие на бэкенд и показывает отправленное сообщение в

RabbitMQ.  
RabbitMQ является системой, оригинально разработанной для работы по протоколу AMQP. 
Это бинарный протокол, в котором используется клиент -серверная коммуникация между 
каналом и клиентом канала в форме определенных команд, что сближает его с протоколами 
типа RPC. Сторона коммуникации, которая имеет сообщение для отправки, посылает команду 
стороне, которая должна его принять, и э та команда синхронно обрабатывается. Например, 
если сервис А хочет послать сообщение сервису Б, то он инициирует коммуникацию с 
RabbitMQ, после чего RabbitMQ в том же порядке инициирует коммуникацию с сервисом Б. За 
счет того, что все участники коммуникации не имеют представления о загрузке своих 
контрагентов, такая схема более уязвима к высоким нагрузкам; кроме того, сервер RabbitMQ 
должен инициировать все виды коммуникаций с клиентами канала, что приводит к тому, что 
пропускная способность всей системы ограничена его ресурсами CPU.

RabbitMQ оперирует понятиями точек обмена (Exchange) и очередей (Queue).  Сообщение 
посылается в точку обмена, после чего по определенным правилам фильтрации передается в 
очередь, на которой слушает получатель этого сообщения. Очередь связывается с 
получателем и инициирует получение им сообщение. Если на очереди слушает несколько 
получателей и если для очереди сконфигурирована надежная доставка, то может получиться 
так, что сообщения перемешаются и более старые будут доставлены в одного получателя 
позже, чем  более новые.  О сновной моделью RabbitMQ является модель производители -
потребители, для реализации модели писатели-читатели требуется создание нескольких 
очередей, на каждой из которых будет слушать свой читатель. Также для точки обмена может 
быть настроена устойчивость, которая бывает двух видов – с гарантией доставки и с гарантией 
обработки.  
В целом, RabbitMQ показывает себя достаточно сложным в настройке и слабо толерантным к 
высоким загрузкам, поэтому  основным применением технологии являются не слишком 
загруженные системы, в которых требуется выполнение вычислительно тяжелых и ли 
длительных задач. Например, серверная генерация документов, изображений, сложные 
вычисления, работа с SOA могут выполняться с помощью RabbitMQ, так как основная нагрузка 
здесь ложится не на канал данных, а на потребителей сообщений. В задачах, в которых 
необходимо доставлять огромное количество сообщений, не требующих сложной обработки, 
например, чтобы показывать онлайн статус по льзователей мессенжера, RabbitMQ 
существенно проигрывает Kafka.  
Kafka. 
Kafka является системой, устроенной по логике, во многом являющейся диаметрально 
противоположной RabbitMQ. Основной задачей Kafka является репликация журнала 
сообщений. Журнал сообщений публикуется в топике (topic) и нарезается на партиции 
(partition) в соответствии с настройками это го топика . Например, топик может быть 
сконфигурирован в  четыре партиции, соответственно, журнал сообщений будет нарезан 
примерно на четыре части в соответствии с некоторой хеш -функцией. Партиция является

Kafka гарантирует, что в рамках одной партиции сообщения не могут перемешаться, что 
достигается тем, что у одной партиции в рамках одной группы серверов может быть только

реализовать модель писатели - читатели, то каждого читателя должна быть своя группа 
серверов.  
Каждая партиция, в зависимости от сконфигурированной степени устойчивости топика, может 
обрабатываться одним или несколькими брокерами, входящими в кластер Kafka. Один из этих 
брокеров является мастером партиции, а остальные – репликами. Вопрос о том, какой именно 
брокер является мастером партиции, решает брокер – лидер топологии. Этот брокер до 
версии Kafka 3.0 выбирается с помощью кластера zookeeper , который является необходимой 
частью инсталляции. В версии 3.0 и выше Kafka имеет возможность самостоятельн о решать 
проблему выбора лидера. 
Клиенты (консьюмеры) топика распределяются по партициям; если их больше, чем партиций, 
часть клиентов простаивает. Если их меньше, чем партиций, то часть клиентов имеет 
несколько связанных партиций. Если какой -либо из клиентов отказал, выполняется 
перераспределение клиентов по  партициям. Далее важным отличием от RabbitMQ является 
то, что клиент инициирует получение сообщений с сервера, а не наоборот. На стороне брокера 
содержится специальный системный топик, указывающий, до какого места была прочитана 
партиция определенной сервер группой, и начиная с этого места клиенту выдаются 
дальнейшие сообщения. Эта модель гарантирует, что события всегда будут обработаны в 
одном порядке в рамках партиции, а также дает возможность выполнять пакетную обработку 
и гарантированную обработку, так как клиент, обработав пакет сообщений, может сообщать  
мастеру партиции об этом факте (выполнять commit партиции). 
Kafka не гарантирует высоких скоростей доставки индивидуальных сообщений, однако в

неудобству развертывания приложений на физических машинах. Можно отметить следующие 
причины, почему физические машины не подходят для микросервисной архитектуры: 
1 Серверное оборудование крайне дорогое; писать приложения так, чтобы максимально 
эффективно его использовать достаточно сложно. Необходимые ресурсы для 
приложения могут быть существенно меньше, чем ресурсы одного сервера. 
2 При необходимости наращивания мощностей приложения требуется физическая 
покупка сервера, физический монтаж сервера и физический монтаж сетевой 
инфраструктуры.  Эти действия не подлежат автоматизации, при этом цикл покупки 
оборудования может занимать месяцы. 
3 Крайне сложными и дорогими становятся схемы обеспечения высокой доступности, 
особенно связанные с распределением трафика по нескольким датацентрам. 
4 Все вышесказанное осложняется ограниченными ресурсами датацентр ов, которы е, 
обычно, име ют предел в наращивании веса оборудования, потребления питания и 
выделения тепла.

Контейнеризация. Docker.  
 
Несмотря на преимущества виртуальных машин они, все -таки, не свободны от недостатков. 
Прежде всего, операционная система внутри виртуальной машины потребляет существенные 
ресурсы на работу тех сервисов, которые для работы приложения не нужны. Поэтому 
следующим шагом виртуализации явилась контейнеризация – выделение изолированных 
процессов в рамках хост -системы. Такая модель изоляции процессов иногда называется 
софтверной виртуализацией. 
Процессы-контейнеры являются особыми процессами, которые максимально изолированы от 
адресного пространства процессов хост -системы. Они не являются виртуализацией 
оборудования в прямом смысле, вместо этого операционная система на логическом уровне 
контролирует их доступ к адресному пространству хост машины, создавая видимость того, что 
такой процесс работает один , в своей собственной файловой системе и своем собственном 
сетевом окружении . В виду особенностей реализации и архитектуры операционных систем 
наиболее эффективны такие процессы на ядре Linux. 
На данный момент ведущей системой контейнеризации является Docker.  Он состоит из трех 
основных компонент – клиента, хоста и реестра.  Хост оперирует объектами контейнеризации, 
такими как образами (имиджами) контейнеров и их запущенными экземплярами. При 
необходимости хост может взять имидж контейнера и запустить, либо остановить уже

Docker desktop. 
 
Docker является важным шагом вперед в области виртуализации, однако, и он не свободен от 
некоторых проблем. Прежде всего, достаточно неудобно управлять контейнерами по одному, 
так как приложение, обычно, состоит из многих контейнеров. Промышленные системы 
управления контейнерами, такие как Kubernetes, имеют развитую инфраструктуру и средства 
управления параметризацией и развертыванием, которые могут использоваться для создания 
сложных контейнерных агрегатов. В целях разработки, однако, обычно используют бол ее 
простые инструменты, такие как Docker Desktop.

содержится в файле docker-compose.yml. Чарт содержит в себе описание всех используемых

Собственно, информация о запускаемых контейнерах начинается с раздела services. Далее 
идет имя, которое мы даем сервису ( postgres), и базовый имидж. Через имя сервиса другим 
контейнерам, находящимся в той же сети, будут доступны соединения с этой базой (это имя 
виртуального хоста). Переменные среды указывают, как будет называться база данных и 
пароль для пользователя postgres. Раздел volumes нужен для того, чтобы смонтировать скрипт 
по первичному заполнению базы данных, лежащий в текущем каталоге (все скрипты, 
лежащие в docker-entrypoint-initdb.d, будут выполнены при первом старте контейнера). 
Наконец, раздел ports указывает, что порт 5 432 виртуального хоста нужно транслировать в 
порт 6432 хост-машины, исполняющей Docker Desktop. 
Следующий сервис – это приложение myapp, которое запускается из контекста demo, в 
данном случае, каталога с файлом Dockerfile, в котором лежит Java приложение. Разделы links 
и depends_on указывают Docker Desktop на наличие сетевой связности с базой данных и 
необходимость стартовать приложение только после старта базы соответственно. 
Приложение будет доступно извне по порту 9443, куда будет транслирован порт 8443 
виртуального хоста. 
Запустить такое приложение можно командой docker-compose --build up 
 
Задание на лабораторную работу. 
 
1 Подготовьте Ваше приложение к разворачиванию в облачном сервисе или 
компоненте Docker. 
2 Реализуйте файл docker-compose.xml, который будет содержать все необходимые для 
работы Вашего приложения ресурсы 
3 Внимание. В виду того, что далеко не на каждом компьютере можно запустить 
систему виртуализации, данная лабораторная работа сдается в электронном виде, без 
демонстрации преподавателю.
